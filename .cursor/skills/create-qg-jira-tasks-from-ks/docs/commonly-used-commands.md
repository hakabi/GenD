# Standard Operation Guide: Common Commands & Usage Meaning

## 1. Overview
The `create-qg-jira-tasks-from-ks` skill is specialized for automating the synthesis of requirements from KS-series Jira tickets into a standardized testing structure (Epic ➔ Parent Task/Story ➔ Sub-task) within the QG project.

Key capabilities:
- **Standardized QA Formatting**: Enforces a strict QA template format on 100% of the generated tickets (Test Objective, Preconditions, Test Steps, Expected Result). Missing data is automatically populated with `[TBD...]` placeholders.
- **Metadata Synchronization**: Automatically assigns tickets to the designated QA engineer and pushes them directly into the QG board's Active Sprint.
- **Automated Documentation**: Draft structures and synthesized requirements are auto-saved locally into `_requirements.md` and `_QG-Jira-Task-Structure-Preview.md` files serving as reference logs / audits (prefixed with the smallest KS ID).
- **Ad-hoc Task Reorganization**: Automatically scans manually created Jira issues within an Epic and groups them logically into corresponding Parent Tasks (Phase 6).

## 2. Commonly Used Commands & Business Meaning

The skill handles context well, but below are the optimized prompt templates for the main use cases:

### Case 1: Full Feature Onboarding (New Epic + Tasks)
- **Meaning/Intent:** Use this only when starting a brand-new feature that doesn't exist on Jira yet. It builds the root Epic and the initial task structure in one flow.
- **Command Syntax (Full):** 
  > `@[/create-qg-jira-tasks-from-ks] I have tickets KS-934 and KS-939. Please analyze the requirements and create a new Epic containing the entire QA testing structure.`
- **Command Syntax (Shortened):**
  > `@[/create-qg-jira-tasks-from-ks] Create QG hierarchy from KS-934, KS-939.`

### Case 2: Standard Task Generation (Linking to Existing Epic)
- **Meaning/Intent:** Use this when an Epic already exists (e.g., QG-83) but you need to populate it with its main hierarchy of parents and sub-tasks for the first time.
- **Command Syntax (Full):** 
  > `@[/create-qg-jira-tasks-from-ks] Read tickets KS-934 and KS-939 to generate QA tasks. Do not create a new Epic; link all tasks into existing Epic QG-83.`
- **Command Syntax (Shortened):**
  > `@[/create-qg-jira-tasks-from-ks] Create tasks from KS-934, KS-939 for Epic QG-83.`

### Case 3: Requirement Injection (Appending New KS Tickets)
- **Meaning/Intent:** Use this for "Change Requests" or additional scope. It analyzes a new KS ticket and injects the new tasks into your existing Epic without duplicating existing work.
- **Command Syntax (Full):** 
  > `@[/create-qg-jira-tasks-from-ks] Dev just added ticket KS-999. Please append this requirement into the structure of Epic QG-83. Analyze it to create additional Parent Tasks or Sub-tasks accordingly.`
- **Command Syntax (Shortened):**
  > `@[/create-qg-jira-tasks-from-ks] Append KS-999 requirements to Epic QG-83.`

### Case 4: Maintenance & Cleanup (Grouping Manual Tasks)
- **Meaning/Intent:** Use this for "Housekeeping". If the team added tasks manually on the Jira UI, this command scans and groups them under the correct parent folders/containers for a clean board.
- **Command Syntax (Full):** 
  > `@[/create-qg-jira-tasks-from-ks] Please group the manually created tasks inside Epic QG-83 into their appropriate Parent Tasks.`
- **Command Syntax (Shortened):**
  > `@[/create-qg-jira-tasks-from-ks] Group manual tasks in Epic QG-83.`

## 3. Workflow Execution (6 Phases)

Whenever the Skill is triggered, the system executes the following sequence:
1. **Phase 1 (Data Ingestion):** Calls APIs to read `summary`, `description`, and `comments` from the provided KS IDs to gather complete context and requirements.
2. **Phase 2 (Synthesis & Documentation):** The system decomposes the logic into an Epic ➔ Parent ➔ Sub-task hierarchy. It auto-saves this matrix into `task-analysis-records/[Smallest-KS-ID]_requirements.md`.
3. **Phase 3 (Preview):** Displays the preview screen for human UI review and saves `task-analysis-records/[Smallest-KS-ID]_QG-Jira-Task-Structure-Preview.md`. (Automation stops here and waits for the user to type "Continue" or "Proceed").
4. **Phase 4 (Jira Creation):** Executes MCP calls to create Parent Tasks and Sub-tasks based on the approved layout. Strict QA formats are injected, filling Assignee, current Sprint, and summary prefixes (e.g., `Feature Name - ...`).
5. **Phase 5 (Reporting):** Outputs the success logs and Jira ticket URLs.
6. **Phase 6 (Ad-hoc Reorganization):** Organizes "orphan" tasks created manually and links them back to standardized parent tasks.

## 4. Forced Formatting Standards

Regardless of what AI parses or what is added manually, every ticket generated by this Skill is forced into the following structural templates. Missing information falls back to `[TBD]`.

**Epic Format:**
```markdown
*Epic Overview:*
(Epic overview here)

*Scope:*
(Testing scope)

*Preconditions:*
(Prerequisites)

*Exit Criteria:*
(Completion criteria)
```

**Parent Task (Story) & Sub-task Format:**
```markdown
*Test Objective:*
(Objective of the test case)

*Preconditions:*
(Preparation steps - Needs User definition if missing)

*Test Steps:*
1. (List of steps - Needs User definition if missing)

*Expected Result:*
(Hyper-specific expected outcome determined strictly from KS ticket context)
```
