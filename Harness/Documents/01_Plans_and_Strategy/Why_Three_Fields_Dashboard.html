Harness · Aloha Test Classification
The question · is "feature + label" enough?

The field count isn't the fix.
Closing the vocabulary and namespacing is.

A test case is never one thing — area, intent, run purpose, fund scope, environment. Harness already has the three fields to hold them: feature, category, labels[]. The collapse isn't about how many fields — it is that they are free text. Close them, and namespace labels[], and the vocabulary grows by addition instead of multiplication.

Fold just four real dimensions (area × fund × environment × priority) into the feature field and the arithmetic already predicts ~240 distinct values. The live catalog has 203 feature values. That is not a coincidence — it is the same multiplication, and free-text titles pile on top to make it worse. Keep the dimensions separate inside namespaced labels[] and the same information costs ~45 governed values in total.

The proposal is THREE FIELDS — the debate is two disciplines, not field count. Both today and the proposal use the three fields Harness already has: feature · category · labels[]. What decides everything is (1) closing the vocabulary and (2) namespacing labels[]. The comparison below runs on those two: A free-text (today) → B closed but flat labels → C closed + namespaced (the proposal). See De_Xuat_Phan_Loai_3_Truong_VN.md.

The proof, from your own data

The most common value in the catalog, public-fund-risk, is two fields fused into one token. That single fusion is why "Risk" already exists as twenty different values.

Split back into two fields, the fund becomes a labels: fund:public tag and the area collapses to a single risk value shared by all four funds. That one move is what turns twenty Risk values into one, makes --grep @risk return every Risk case, and lets a coverage grid finally count them. Refuse the split and you keep public-fund-risk, total-endowment-risk-tab, risk-dashboard … — the same test area, filed where no one else thinks to look.

The discipline — and how far it goes

The rules that decide what earns a namespace in labels[]

The same reasoning that adds a metric: namespace also refuses a needless one. A dimension earns its own namespace only if it passes all three tests — which is also why fund and metric must leave feature.

TEST 01

Orthogonal

Its value varies independently of the others. A Risk test can be positive or negative, smoke or regression, on the public or private fund. If a dimension always moves with another, it isn't a new dimension — merge it.

TEST 02

Answers a unique query

It answers a question no other namespace can. "What re-runs if NAV changes" can only be asked of metric:; "run smoke before deploy" only of suite:. Drop the namespace and that question is gone.

TEST 03

Cutting it multiplies

Folding it into feature multiplies the vocabulary instead of adding to it. Fund into feature = area ×4. This is the test that forces fund/metric/env out of feature and into namespaced labels[].

This is a ceiling, not a licence to grow. The same rule freezes feature at 10 areas (2 levels deep, max), holds test types at 5, and defers accessibility until it earns a namespace. Closed + namespaced is the minimum discipline that answers every real query — not empire-building, and not open-ended. It is the smallest scheme that doesn't fragment.
Bottom line for the decision

"Just use feature + label" is not the simpler option — it is the state you already have.

Free-text / flat labels

  • Free-text lets every dimension fuse into feature → multiplicative explosion (the measured 203).
  • Loses or blurs the cross-cutting questions — impact analysis, suites, fund scope, environment, traceability.
  • Keeps feature fragmenting: twenty Risk values, --grep @risk broken.
  • Coverage dashboards report confidence built on single-use values.

Closed + namespaced (3 fields)

  • Additive vocabulary — ~45 governed values for ~300 cases, not hundreds.
  • Every question answerable with one typed query; one screen, auto-filled at ingest.
  • Risk = one value across all funds; heatmap and impact queries actually work.
  • Frozen by rule — no new value or namespace without passing all three tests.
This isn't extra work for QA. They are the three fields Harness already has, filled automatically, so QA writes plain English and confirms a preview. The win isn't the field count — it is closing the vocabulary and namespacing labels[]. Drop those two disciplines and you are back at 203.
