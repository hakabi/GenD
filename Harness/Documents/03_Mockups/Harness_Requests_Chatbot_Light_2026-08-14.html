One assistant, three places it can live

A Q&A assistant that answers how-to, data, Aloha and prompt-quality questions, suggests actions but never takes them alone, and appears as one assistant with two entry points. Each placement below follows the organizing principle of its parent direction — so the assistant reinforces the layout instead of floating on top of it.

Two constraints this design has to respect

CONFLICT
There is already a chat in Harness

The New Request dialog opens with “What would you like to test?”. A second, unrelated chat would give users two boxes that look identical and behave differently. This design treats them as one assistant in two modes — the New Request panel is the assistant with the current draft in scope.

GROUNDING
Every answer shows its source

An assistant that answers from a catalog where ~51% of cases have no link back to their request will be confidently wrong sometimes. Citations are not decoration here — they are how a QA decides whether to believe it, and how they notice when data is missing.

Answers cite their source. Actions always ask first.

1

Scope chip

States what the assistant can see, in plain words. Removes the most common chatbot confusion — does it know what I'm looking at? — and is the only thing that changes between the Requests page and the New Request dialog.

2

Answer that leads with the verdict

First line is the conclusion, not the preamble. “The test passed — saving it didn't” before any explanation. Same principle as Direction A's verdict card.

3

Citations

Every factual claim links to the step, case, run or knowledge file it came from. Given that ~51% of cases lack request provenance, the assistant must also be able to say “I don't know why this case exists” — a missing citation is information too.

4

Action card — suggest, then confirm

Actions never fire on their own. The card names the action, states its blast radius (“won't re-run the test against Aloha”), and offers a refusal that costs nothing.

5

Suggested follow-ups

Generated from current state, not a fixed list. They teach what the assistant can answer — which matters most for the first-time QA/BA who doesn't know what to ask.

If you want my recommendation

Build the component once, ship it in New Request first. That entry point needs no query layer and no live catalog access — the duplicate check already exists in Spec 039, and the validation rules are deterministic. It also fixes a failure QA has already reported, so it earns trust before the assistant is asked anything hard.

Then add C · Guide, then A · Companion. C is mostly curated content, so it's cheap and its answers can't drift. A follows once the plain-English failure mapping exists — which Direction A needs anyway, so the cost is shared.

B last, and only after the provenance fix. An assistant that answers “which cases failed and why” across a catalog where half the cases can't explain their own origin will produce confident, wrong answers — and one of those costs more trust than the feature gains. Fix the link first, then let it read the catalog.
