Test case UI — three directions

All three answer the same four questions: how a case is found, how it is judged, how conflicts are resolved, and how its health is read. They differ in what they put at the centre.

The live system has moved a long way since these were conceived. Reviewing it changed the conclusion: this is now less a choice between three designs than a map of what already exists, what needs finishing, and what is genuinely new. Read the section below before the mockups.

What is live today

Test cases now sit under three sub-tabs. Much of what these designs propose is already present in some form.

Failed built

A triage console. Five counters — 87 failing · 0 app bug · 1 test script · 0 new feature · 86 needs triage. Filters on search, feature, labels and reason. Case detail with Info · Steps · History · Groups, a screenshot slot, raw error output, editable feature & labels, and a Triage block with Reason and Notes.

All cases built

A real catalog table — Case | Feature | Project | Triage | Last run — with Configure columns, a status filter, bulk checkboxes, a Run action, and a side panel that keeps list context.

Executed history built

Runs as first-class objects. Run | Case | Status | AI | Auto | Completed, with a detail panel carrying run ID, spec path, return code, failed step, AI steps, automation, AI fallback, telemetry state and session — plus View request and Re-run.

The gap is not features — it is data reaching them 86 of 87 failures sit at "Needs triage" and every row in All cases reads unlabeled, so the taxonomy is built but unused. FAILED STEP renders as an em dash — the field exists, nothing populates it. Telemetry reports "Incomplete" and the AI, Automation and AI-fallback counters all read zero. And feature drift is visible in the catalog: clean values such as auth and cash-forecast sit beside truncated titles like application-loads-without-redirect-loop-and-disp.
A

Familiar — today's Harness style, extended

Keeps the current three-column shape and the existing teal-on-light visual language, and adds the two things missing: a feature tree for grouping, and a segmented switch between the review queue and the catalog. Lowest change cost of the three; a current user would need no explanation.

Coverage — the freestyle direction

Built around what makes Harness different from a test-management tool: cases are generated to fill gaps, and their trustworthiness varies. The home screen is not a list but a coverage matrix — feature by category — where an empty cell is the most important thing on the page, and a request is understood by which gaps it fills.

The dependency, now confirmed against the live system Every design groups by feature and splits by category. This was previously a caution based on a measurement taken on 6 August. It is now confirmed live: the catalog shows clean feature values such as auth and cash-forecast sitting beside truncated titles used as grouping keys, and the Triage column reads unlabeled on every row. Until this is resolved, A degrades to a flat list, B's new columns have nothing to show, and C's matrix cannot be drawn at all.

Recommendation

Reviewing the live system changes the conclusion. The screens are further along than these designs assumed, and what is missing is mostly data reaching screens that already exist. Suggested order:

#ActionWhy it comes first
1Establish why triage is not happening86 of 87 failures are unlabelled. The taxonomy is built and unused, so this is a workflow or ownership question rather than a design one. One conversation with QA, no build
2Populate FAILED STEPThe field is already rendered and always empty. Filling it is the highest-value change available and needs no new interface. This is QG-139 #6
3Complete the run telemetryAI, Automation and AI-fallback counters read zero and Telemetry reports Incomplete. Fixing this unlocks C's Trust panel without building C
4Extend All cases toward direction BGoverned columns, sortable headers, saved views, plus muted and flaky as real state. An extension of shipped work, not a rebuild
5Add C's Trust panel into B's side panelHuman-verified, AI-fallback usage, stability, staleness. Highest-value addition once step 3 is done
6Hold C's coverage matrixRevisit only after classification lands and the feature axis is clean

Direction A should be dropped. The live build has overtaken it; its only remaining contributions — the feature tree and saved views — are absorbed into step 4.
