Anatomy of the Requests list

This is Frame 1 of the navigation mockup, pulled out and annotated. It is the page a QA lead opens first every morning, so everything on it should answer one of two questions: is anything waiting on me? and what came out of the thing I submitted? Sixteen elements are numbered below. Work through them in order; each one ends with an amber strip naming the decision we owe.

A · The page header

Elements 1–4 What the page is, and the two buttons that sit above everything else
1Page title — “Requests”header, left
What is it

The page heading. It names the object you are looking at: a request is one prompt somebody submitted in order to generate test cases.

What it is for

Orientation, and it is the anchor for the breadcrumb on the detail page (← Requests / REQ-1042).

Options / choices
  • Keep the plain noun Requests — matches the left nav item, so there is nothing to learn.
  • Rename to Generation requests or Prompts — more literal, but it breaks the match with the nav.
Decide in the workshopDoes everyone in the room actually agree on what a “request” is? It is a prompt, and the thing of value is the cases it produces. If half the room hears “request” and thinks “ticket”, that mismatch will follow us through every other screen.
2The count — “24 · 2 need you”header, beside the title
What is it

Two numbers: how many requests are in the list right now, and how many of those are waiting on a human decision.

What it is for

Tells you whether there is anything to do before you read a single row. On a quiet morning you read “24 · 0 need you” and close the tab.

Options / choices
  • Scope of the first number: all requests, or only those matching the active filters? Recommend it follows the filters, otherwise it contradicts what you can see.
  • Is “2 need you” clickable? Clicking it could apply the Needs me filter — one gesture instead of two.
  • Does it also appear as a badge on the left nav so you see it from any page? That would be the only change this proposal makes to the nav, so it needs its own yes.
Decide in the workshopIs “needs you” personal or team-wide? Harness has no assignment concept today, so “you” can only mean “requests I submitted”. A QA lead reviewing everybody’s output would then always see zero. Settle this once, here — elements 5 and 14 both depend on the answer.
3Configure columnsheader, right · secondary button
What is it

Opens a small panel to show, hide and reorder the columns of the list.

What it is for

The list serves two different people. A lead scans for blockers; an author checks one submission. Rather than argue about the default, let each person keep their own.

Options / choices
  • Scope of the saved layout: per user (simplest) · a team default that a user may override · named, shareable presets (“Triage”, “My work”).
  • Locked columns: Request almost certainly cannot be hidden. Prompt probably not either, since it is the only description that exists.
  • Drop it entirely for v1 and ship one agreed column set.
Decide in the workshopDo we build column configuration at all in the first release? Cutting it is cheap, and it forces a useful argument: if we cannot agree on one default column set in this room, that is a sign the page is trying to serve two jobs and may need two saved views instead.
4New requestheader, far right · primary button
What is it

The primary action. Opens the creation dialog where you write the prompt and pick the request mode and session.

What it is for

It is the one thing most people come to this page to do, so it gets the only filled purple button on the screen.

Options / choices
  • Where the form lives: keep today’s modal, or a full page at /requests/new, which would be linkable and would survive an interruption.
  • Prefill: “Duplicate this request” from a row, so a failed prompt can be edited rather than retyped.
  • Templates per project or feature area, if prompts turn out to be highly repetitive — which the sample rows suggest they are.
Decide in the workshopShould Fix & retry (element 14) simply be New request with the prompt prefilled? That would give us one creation path instead of two, and it is the natural fix for a request that produced no cases.

B · The filter bar

Elements 5–9 Four chips and a freshness stamp. This row is what turns a 24-row list into a worklist
5Needs mefilter bar · toggle, shown active
What is it

A toggle, not a dropdown — the only one in the row. On means: show only requests that are waiting on a decision from me. It carries its own count.

What it is for

The highest-value control on the page. It collapses 24 rows to 2 and answers the morning question in one click.

Options / choices — what should count as “needs me”?
  • a. Cases were generated and are waiting to be accepted or rejected (“3 to review”).
  • b. Generation produced nothing and the prompt needs fixing (“Fix & retry”).
  • c. A case from this request is failing when it runs (“1 failing”).
  • All three together — simple, but then the chip means “something is wrong or waiting”, which is vague.
  • Split into two chips — Needs review and Needs fix. More precise, more clutter.
Decide in the workshopPick the definition, and pick the word. If the answer to element 2 is that we have no assignment, then honestly this chip is Needs someone, not Needs me — and it should be labelled that way rather than quietly meaning something different from what it says.
6Outcome (filter) partly shippedfilter bar · dropdown
What is it

Filters the list by what the request produced — not by its internal job status.

What it is for

Separates two questions we currently run together: did the machine finish its job? and did it actually produce anything useful?

What already ships — Filter by status

The live page already has this dropdown. Its seven values are Successful · Running · Awaiting review · Pending · Rejected · Duplicate · Failed, plus All statuses. So this is not a new filter. What is proposed is a change of meaning, not a change of control.

Options / choices — status, or outcome?
  • Keep the shipped status list. Zero work. It reports the state of the job.
  • Re-derive it as Outcome — Cases created · Running · No cases produced — computed from the output rather than from the job flag.
  • Show both, keeping status for debugging and outcome for scanning. More honest, more clutter.
Decide in the workshop — start from the shipped list, not a blank page The vocabulary already exists; the question is whether it is the right one. Here is the concrete failure it allows: a request that produced zero cases can sit in the list reading Awaiting review, because the job finished cleanly even though nothing came out of it. Status describes the machine; Outcome would describe the result. Whatever we choose, the column (element 12) and the header count (element 2) must read from the same field as this filter.
7Author (filter) already shippedfilter bar · dropdown
What is it

Filters by the person who submitted the request.

What it is for

Two jobs: “show me only my own” for an individual, and “show me what this person is producing” for a lead.

What already ships — Filter by owner

The live page has this dropdown with three entries — My requests (and it is the default), All requests, and By email…. The queue card already prints the author too. “Find my work” is therefore solved. The gap is narrower than the mockup implies.

Options / choices — what is still missing
  • “By email…” means typing an address from memory. There is no list of who has actually submitted, so a lead cannot browse the team.
  • Replace it with a picker populated from real submitters — short, accurate, no typing.
  • Single-select or multi-select? A lead may want two team members at once. Today it is single.
  • Show raw usernames, or display names if SSO gives us them (see element 15).
Decide in the workshopGiven this already works, is anything here worth doing at all? The one real gap is that “By email…” requires knowing the address in advance — fine for finding yourself, useless for reviewing a teammate. Also: is Author the right word for a non-QA audience? The person wrote a prompt, so Submitted by may be plainer. Whatever we pick, the filter and the column must use the same word.
8Feature (filter)filter bar · dropdown
What is it

Filters by the product area the request targets — risk / dashboard, cash-forecast / historical-flows, and so on.

What it is for

It is the bridge from “requests” back to “the product”. Coverage conversations happen by feature area, never by request.

Options / choices
  • Shape: one flat list, or two levels (area, then sub-area) matching the risk / dashboard pattern.
  • Where the value comes from: inherited from the generated cases, or chosen by the author when submitting. Inherited is automatic, but it means a request with no cases has no feature.
  • Free text, or a controlled list drawn from the Aloha taxonomy.
Decide in the workshop — and this one has a known data problem verify with dev Live feature values are being cut off mid-word at roughly 47 characters — for example application-loads-without-redirect-loop-and-disp. A truncated value cannot be a reliable filter key, because two different features can collapse to the same string. Confirm the real limit before we design a picker on top of it.
9Updated 30s agofilter bar, right
What is it

A freshness stamp for the whole list.

What it is for

Generation is asynchronous and can take minutes. Without this you cannot tell a quiet system from a stale page.

Options / choices
  • Auto-refresh on a timer (say 30s) · a manual refresh button · live push from the server.
  • How new rows arrive: inserted silently, or held behind a “3 new requests — show” bar.
  • Whether a row that changes underneath you is highlighted for a moment.
Decide in the workshopSilent insertion while somebody is mid-scan moves the rows under their cursor and is genuinely disorienting. Recommendation: refresh the counts live, but hold new rows behind a “show new” bar.

C · The list itself

Elements 10–16 One row is one request. Seven columns, then the behaviour of the row as a whole
Cut from this hand-out: the row checkbox — and why the cut matters An earlier draft opened this zone with a checkbox column for selecting several requests at once. It has been removed. It was never observed in Harness — it was carried across from Test cases › All cases, which really does have bulk select. The live Requests queue is single-select; its own subtitle reads “select a row to inspect activity and open case review.”

The API settles it. Every request endpoint takes one id — /retry, /archive, /void — and there is no delete endpoint for a request at all; a request can only be archived or voided. The single batch route in the whole 141-route API belongs to the case catalog, which is exactly why All cases has bulk select and this page does not. Every bulk action a checkbox implies would need new backend work.

And the one bulk operation that genuinely exists needs no selection at all: POST /api/quests/requeue-failed-duplicates takes no id and acts on the whole collection. If we ever do want bulk here, that shape — a button, not a checkbox — is the precedent to follow.
10Request new fieldcolumn 1 · the key
What is it

A short, human-readable key such as REQ-1042, styled purple. The whole row is the click target — the coloured key is simply what tells you the row is clickable.

What it is for

Something you can say out loud in standup and paste into Jira or Slack. This is what makes a request referable at all.

Options / choices
  • Sequential key per project — REQ-1042. Readable, sortable, familiar from Jira. Needs a sequence generator.
  • Short hash — REQ-8f3a. No sequence needed, but not sortable and harder to read aloud.
  • Keep the UUID fragment as today — #1ad3fee0-31d. Zero work, and unusable in conversation.
Decide in the workshopThis is probably the cheapest single improvement on the page, and it is a dev decision rather than a design one. Today the list shows a UUID fragment that nobody can repeat from memory.
11Promptcolumn 2 · flexible width, 2-line clamp
What is it

The raw text of the request, exactly as it was typed, clamped to two lines so that every row is the same height.

What it is for

It is the only description that exists. There is no title field on a request — not hidden, not empty: it does not exist.

Options / choices
  • Keep the raw prompt — what is drawn above. Honest, and zero work.
  • Derive a title from the generated spec slug. A slug like risk-model-dashboard-total-risk-table-and-download-report-461dc2 is already produced and stored, just never shown. Three string operations — strip the six-character suffix, hyphens to spaces, capitalise — turn it into “Risk model dashboard total risk table and download report”. No AI involved.
  • Have a model write a title. Best reading, but a cost and a failure mode on every request.
Decide in the workshop — and here is the honest consequence We provisionally chose to keep the raw prompt. The cost is that rows still look alike at a glance, because every prompt opens with the same Project: aloha / Go to workbench-app.lab.gend.vn boilerplate — look at the five rows above and see how far you get from the prompt alone. Differentiation then comes entirely from Outcome, Cases, Needs you and Age. If the room finds that unacceptable, the slug option is available and small.
12Outcome new fieldcolumn 3 · 138px
What is it

A plain-language sentence about what came out: 15 cases created · Running · 2 of 5 · No cases produced.

What it is for

Answers “what did this produce?” in one glance. Critically it is computed from the output, not read from a status flag — so a failed generation can never display as if it were waiting for review.

Options / choices
  • Colour: green created · blue running · red none. Or no colour at all, leaving colour to the Needs you column alone.
  • Progress while running: “2 of 5” as text, or a thin progress bar.
  • Whether it carries a timestamp (“created 2h ago”) or leaves that to Age.
Decide in the workshopConfirm that Outcome is derived, never stored. The moment somebody writes it into a status field it can drift out of step with reality, and we are back to today’s problem — a request that says “done” while having produced nothing.
13Cases new fieldcolumn 4 · 66px, numeric
What is it

The number of test cases this request produced. Set in a tabular-figures font so the digits line up down the column.

What it is for

It is the sortable version of Outcome. “Show me everything that generated nothing” is one click on this header.

Options / choices
  • One number (15) or a breakdown (15 total · 12 ready · 3 to review).
  • Whether 0 is styled as an error, as drawn, or left neutral because Outcome already says so.
  • Whether the number is itself a link into the detail page’s Cases tab.
Decide in the workshopCases and Outcome overlap — “15 cases created” next to “15” is saying the same thing twice. Keep both, because one reads and one sorts? Or drop one? Dropping Outcome loses the plain sentence; dropping Cases loses the sorting.
14Needs you new fieldcolumn 5 · 100px
What is it

A small coloured label naming the action this row is waiting on: 3 to review, Fix & retry, 1 failing, or an em dash when nothing is needed.

What it is for

This is what a QA lead scans first. It is deliberately a column rather than a badge on the row, so that it sorts, filters, and can be read straight down.

Options / choices — the value list
  • n to review — amber. Cases generated, waiting for accept or reject.
  • Fix & retry — red. Generation produced nothing; the prompt needs work.
  • n failing — red. An accepted case is failing when it runs.
  • — — nothing needed. Deliberately a dash rather than the word “None”, so the eye skips it.
  • Should clicking the value jump straight to the right place? “1 failing” could open ?tab=execution directly.
Decide in the workshopSame unresolved question as elements 2 and 5: who is “you”? Also worth asking — can a row need two things at once, three cases to review and one failing? If yes, we need a rule for which one wins, or the column has to stack them.
15Author (column)column 6 · 118px
What is it

The username of whoever submitted the request — nguyenhoangly103, hakhoabinh, glzmaxdinh.

What it is for

Accountability, and the thing the Author filter (element 7) acts on. It also tells you who to ask when a prompt is unclear.

Options / choices
  • Raw username as drawn — accurate, but slow to scan and easy to confuse.
  • Display name from SSO — much easier to read, if the identity provider gives us one.
  • Small avatar plus name, or avatar only with the name on hover — saves roughly 90px of width.
  • Clicking the name applies the Author filter.
Decide in the workshopDo we have display names available from Google SSO? If we do, this is a small change with a real readability payoff. If we do not, the column stays as it is and we should not pretend otherwise.
16Agecolumn 7 · 52px, numeric
What is it

A relative time — 4m, 2h, 1d, 5d — turning red once it crosses a threshold.

What it is for

Finds things that have been sitting. 3h 38m on a request that produced nothing is the signal that somebody submitted it and walked away.

Options / choices
  • Age since created — simple, but then a healthy finished request from last week also looks “old”.
  • Time since the last state change — measures staleness rather than existence. More useful, slightly more work.
  • The red threshold: what number, and does red mean “old” or “stuck”?
  • Exact timestamp on hover.
Decide in the workshopRecommendation: use time since last state change, and only colour it red when the row also has something in Needs you. An old, finished, fully-accepted request is not a problem and should not be shouting.
•The row itself — hover and clickbehaviour, not a column
What is it

Not a visible control, but the most-used interaction on the page. Hovering tints the row and draws a purple accent down its left edge; clicking anywhere on it opens the request.

What it is for

A row that is clickable in only one small spot is one of the most common complaints about list UIs. Here the whole row is the target.

Options / choices — the full interaction set
  • Click anywhere on the row → navigate to /requests/REQ-1042. With no checkbox, the row has no dead zone — every pixel does the same thing.
  • ↑ ↓ then Enter — move through rows and open the focused one. QA working a backlog will use this constantly.
  • Middle-click or Ctrl/Cmd-click → open in a new tab. Free once it is a real URL; impossible with a modal.
  • Esc or browser back → return to the list with scroll position, filters and selection preserved.
  • Hover peek — a small summary card without navigating. Deliberately not designed.
Decide in the workshopThe right-hand preview pane is removed in this proposal — that is what pays for the four new columns. Does the room want the quick glance back as a hover peek? Recommendation: do not build it up front; add it only if QA ask for it after living with the full detail page.

Where the data actually comes from

The rest do not exist yet. That is not a design problem, and no amount of mockup fixes it — it is the honest gap between the screen and the system. Worth putting on the wall during the workshop so that nobody leaves thinking this is a week of front-end work.

Decisions to leave the room with

  • 1 · Who is “you”? Personal, or anyone on the team. Blocks elements 2, 5 and 15 — nothing else can be specified until this is settled.
  • 2 · Status, or Outcome? A seven-value status filter already ships. Decide whether to keep it as-is, or re-derive it from the output so that a request producing zero cases can never read Awaiting review.
  • 3 · Raw prompt, or a derived title? If raw, everyone accepts that rows look alike and that Outcome / Cases / Needs you / Age do the differentiating.
  • 4 · A readable request key. Yes or no, and if yes, sequential or hash. Dev decision.
  • 5 · Bulk actions — already answered, for the record. Out. The API cannot do them, the checkbox column has been cut, and the one real bulk need is already served by a collection-level endpoint. Raise it again only with a dev estimate attached.
  • 6 · Column configuration — in or out of v1? If out, we must agree one default column set before we leave.
