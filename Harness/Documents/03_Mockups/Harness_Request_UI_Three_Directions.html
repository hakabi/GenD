DRAFT — three directions for the Request page. All three use the visual language of test-case direction B so the two pages read as one product, and all three assume case review moves to a fourth Test Cases tab. They differ in what a request is treated as: a delivery, a process, or a filter. Prepared by the Business Analyst, 18 August 2026. Not agreed, not scheduled.

Request page — three directions

The Requests page is the last screen still on the old build. While Test Cases was rebuilt into Failed / All cases / Executed history, Requests kept its 2024-era shape: stacked chrome bands, native dropdowns, hash identifiers and identically-truncated titles.

What the live page does today — observed 18 August 2026 Request #3ae938b9-e89 displays the status AWAITING_REVIEW and a waiting time of 3:38:19. Opening Execution shows the truth: Draft structured intents and Build test steps both FAILED, and the raw cause is printed verbatim — Database error: (code: 1) no such table: tenants. Its one case, Direct test, is PENDING with no steps.

The headline status is telling QA the opposite of the truth. There is nothing to review, and nobody is coming. Every design below is judged first on whether it makes that impossible.
One word, three meanings The queue shows failed for a request whose generation failed, for one whose execution failed, and it shows awaiting_review for one that produced nothing at all. These need different people and different next actions. This is the same finding as the run-verdict vocabulary on the test-case side, and it is the single largest fix available on this page.
R1

Receipt — a request is a delivery

The queue leads with what came out, not what is happening inside. Every row answers one question: did I get test cases, and do any need me? Process detail still exists, but it is secondary and collapsed. Closest in shape to today's page, so the smallest change.

R2

Diagnostic — a request is a process that can break

Built for the situation actually on screen today: generation failing silently. Every row carries a five-segment stage bar, and the detail leads with where it stopped and why, in plain language, with the raw error tucked behind a disclosure. Retry is offered from the stage that broke, not from the beginning.

R3

Source — a request is a filter, not a page

The most literal reading of "requests are just prompts". There is no Requests page. Submitting is a drawer from anywhere; a request becomes a column and a facet in the case catalog, and progress lives in a submissions popover in the header. You never navigate to a request — you filter by one.

Recommendation

R1 as the shape, with R2's failure card inside it. They are not really rivals — R1 decides what a row says, R2 decides what the panel says when something breaks. Together they answer both questions a QA person has, and neither requires removing a page.

Hold R3. It is the most faithful to "requests are just prompts", and it may well be right eventually — but it should not be decided while generation is unreliable. When two requests are stuck for three and a half hours, that is exactly when you want a dedicated place to see and fix them, not a popover.

The change that matters most, whichever is chosen Replace the single word failed with outcomes that name what actually happened: no cases produced · cases created · awaiting review · execution failed · stuck. And never show awaiting_review on a request that generated nothing. That one rule would have prevented the state observed on the live system today, and it costs nothing in layout.
