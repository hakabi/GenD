What each number improves

Each marker on the interface above corresponds to one row here.

ElementTodayThe improvement
1 "Review" replaces "Requests" in the sidebar, with a count of items awaiting action The sidebar shows "Requests" with no indication that anything needs attention. Users must open the page to find out. The count is visible from any screen, so pending review work is never missed. The name states what the page is for.
2 Three states: Needs me · Running · Settled Two dropdown filters (request type and status) that must be set manually on each visit. One click each. The default view shows only work requiring a decision, so the page opens on the task rather than on a list to be filtered.
3 Queue rows lead with the decision required Rows show a truncated prompt, an author and a timestamp. Every row reads almost identically, and the number of test cases is not shown. Each row states 3 need you · 12 ready · 15 cases and how long it has been waiting. The queue becomes scannable and prioritisable at a glance.
4 Lifecycle shown as a single-line spine Progress is spread across the Info, Execution and History tabs, and must be reconstructed by the reader. One line shows where the request has reached and what happened at each stage. Completed stages collapse to a timestamp; the current stage expands into the work below, so the lifecycle frames the content instead of competing with it.
5 Shared classification shown once, at family level Not displayed. Labels and feature are not visible during review. All generated cases inherit the same feature and labels; only the test category differs. Showing them once, marked inherited by all 15 cases, makes the classification reviewable without repeating it fifteen times.
6 Cases needing a decision are separated and placed first All generated cases appear in one undifferentiated list, in generation order. The few cases requiring human judgement are lifted to the top and expanded. The rest are collapsed. Review time is spent only where it is needed.
7 "Extend existing" — a resolution for overlapping cases No such action exists. A case that is a superset of an existing one can only be accepted (creating a near-duplicate) or deleted (losing the new assertion). The existing case is updated with the new assertion instead of a near-twin being created. This is the most common form of overlap and the main contributor to catalog growth.
8 Every conflict shows a comparison and its own resolution options A conflict is reported as an outcome count after the batch completes. What it collided with, and how it differed, is not shown. The colliding case is named and the difference is set out line by line, with the resolutions appropriate to that conflict type. The reviewer can decide without leaving the page or opening the catalog.
9 Cases without conflicts grouped by category, with a single bulk action Each case must be reviewed individually regardless of whether anything is in question. Twelve unambiguous cases become one row and one click, with the option to open them individually. Review effort scales with the number of problems, not the number of cases.
10 Missing categories shown as gaps Categories with no generated cases are simply absent, so their absence is invisible. An empty category is stated explicitly, prompting the reviewer to confirm whether the omission is correct. Coverage gaps are caught at review rather than discovered later.
11 Confirmation summarises the outcome and is blocked until decisions are complete "Confirm and process" is available at all times and gives no summary of what will happen. The action states exactly what it will do — creates 12, extends 1, merges 2 — and stays disabled until every conflict is resolved, preventing a batch from running in an undecided state.

Not included in this proposal

ItemStatus
Comparing two requests side by sideExcluded pending confirmation of demand.
Live monitoring of a running batchExcluded. "Running" is provided as a filter; completion is already reported through the notification area.
The original prompt textAvailable behind View prompt. It is the input that produced the cases, not the subject of the review.
Changes to generation, classification or executionOut of scope. This proposal covers the review interface only.
Implementation note — marker 7 requires backend support Extend existing modifies a test case that has already been approved. It requires version history on the case, an audit entry recording who extended it and from which request, and invalidation of the case's previous run result, since the case has changed. These requirements are specified in the accompanying plan document and should be confirmed with the development team as part of approval.
