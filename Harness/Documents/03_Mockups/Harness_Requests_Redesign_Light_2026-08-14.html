Three ways to make the Requests page explain itself

Each direction below is a different organizing principle, not a different coat of paint. They share one set of fixes and then diverge on the question they answer first. Built on the real tokens.css light palette so any of them can be implemented without new design decisions.

14 Aug 2026 observed live · qops-harness.lab.gend.vn accent #10a37f Epic QG-138

What actually makes it feel messy

01
A request has no human name

Identity is #b52a8284-ee3 — you can't say it in standup or remember it. The title falls back to the prompt's first line, capped at 72 chars. Measured on the live queue: 20 requests, 5 distinct openings, because the informative part sits after the URL.

02
Status is told four times, and disagrees

Header badge FAILED, chips row, Info → Status failed, and "Next step" claiming "Request is still processing" — all on one screen. Live, today.

03
The page never states its own model

A Request proposes Cases which produce Runs. That sentence appears nowhere, which is why "which request does this result belong to" keeps coming back.

04
Chrome outranks content

Title, New request, Show 20, Refresh, then a full-width band showing data/sessions/harness/session-harness-login.json — four rows before the first request.

05
Internals leak into the reader's face

crew_phase_a_draft_intents, "CREW TASK", "Direct test", and a raw branch_checkout_failed git error. None of it is actionable for a QA reader.

06
The best explainer is the most hidden

History → Lifecycle already tells the story cleanly — created, confirmed, executed, failed. It sits in the third tab, behind two noisier ones.

Baseline · what ships today

The current page, annotated

Organizing principle: none stated — the layout mirrors the backend's shape rather than the reader's question.

  • Kills the four-place status contradiction — one verdict, at the top, in a sentence.

New request — split the one question that was really two

Today's single Request mode dropdown mixes what you're testing with whether it runs, which is why "Execute Feature" has no home in the UI.

Click the mode cards and the run toggle — the outcome line rewrites itself.

qops-harness.lab.gend.vn/requests · new
1Describe 2Review proposed cases 3Run

What do you want to test?

Answer two questions and Harness does the rest. You can change everything before anything runs.

1 · What are you testing?

This decides how many cases Harness proposes.

2 · What should Harness do with them?

The step that has no control today — so nobody can tell whether a mode runs or just proposes.

What will happen

Harness will propose exactly 1 test case and then stop and wait for you. Nothing touches Aloha until you press Confirm on the review screen.

Expected to fail on the first run. A bug-ticket test reproduces a bug that isn't fixed yet, so a red result here is the correct outcome — not a problem with your test.
Describe it in your own words REQUIRED

Vietnamese or English both work. Cases are generated using your Knowledge base — 2 files are attached for harness.

✓ What it wins
  • Fixes the review's #1 High severity finding: mode labels now match the documented functions.
  • "Execute Feature" finally has a home — it's the run toggle, not a fifth dropdown entry.
  • The Test-Bug "fails first" rule appears exactly when it's relevant, so a red result stops looking like a defect.
  • Session, environment and knowledge drop into Advanced, where set-once settings belong.
△ What it costs
  • Two questions take more vertical space than one dropdown; the dialog grows.
  • The "what will happen" counts (5–8 cases) are estimates — if they're wrong often, trust erodes.
  • Loses the chat-first feel. Chat can stay as an optional assist, but it's no longer the only door in.
⚙ Build shape
  • Same payload as today — mode plus a new run-now boolean.
  • Mostly a front-end rearrangement of fields that already exist.
  • Lowest effort of everything here, and it's the screen a new QA/BA meets first.

If you want my recommendation

Ship the New request redesign first, on its own. It's the cheapest change here, it fixes the highest-severity finding in your own UX review, and it's the screen a QA or BA from another team meets before anything else — which is exactly the "hiểu liền" goal.

Then take A as the detail and C as the list. They aren't really competitors: A redesigns what you see inside one request, C redesigns how you see all requests. Together they answer both halves of the confusion, and C's cards can open straight into A's timeline.

B is the right answer later — when the queue passes a few hundred requests and triage speed starts to matter more than comprehension. Its table is worth building then, not now, because density is the opposite of the goal you set for this round.
