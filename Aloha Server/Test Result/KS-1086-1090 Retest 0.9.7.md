## Draft comment — KS-1087 · VERIFIED FIXED (one design point to ratify)

**QA verification on build 0.9.7 — PASS**

Re-tested independently on Claude Code (native HTTP), 2026-08-19 03:06 UTC.

**Unknown id:**
```json
{"fund_ids":["99999999"],"start_date":"2024-01-01","end_date":"2024-12-31"}
```
→ `row_count: 0` · `fund_ids_with_data: []` · `unresolved_fund_ids: ["99999999"]` · `returns: []`

**Mixed list:**
```json
{"fund_ids":["500","99999999"],"start_date":"2024-01-01","end_date":"2024-03-31"}
```
→ `row_count: 3` for fund 500 · `fund_ids_with_data: ["500"]` · `unresolved_fund_ids: ["99999999"]`

All three returned dates fell inside the requested window.

The payload carries **`fund_ids_with_data`** as well as `unresolved_fund_ids` — not mentioned in the fix report, and useful: it makes the partial case explicit from both directions rather than requiring the caller to diff two lists.

**One design point for the record.** The response is still `status: success` even when **nothing** resolved. The original ticket allowed this — it asked for an explicit error *or* a structured warning — and the structured-warning route is defensible for agent consumption. But an agent checking only `status` still sees success on a total miss. **Please confirm whether the all-unresolved case should differ from the partially-unresolved case**, or record that it deliberately does not. Same contract question as KS-1090.

**Recommend: close as Fixed**, with the semantics question answered separately.

## Draft comment — KS-1088 · VERIFIED FIXED — and the open question is now closed

**QA verification on build 0.9.7 — PASS**

Re-tested independently on Claude Code (native HTTP), 2026-08-19 03:07 UTC.

**The schema-level root cause is resolved.** `start_date` now carries `pattern: ^\d{4}-\d{2}-\d{2}$` — the constraint it was missing while every `custom_*` sibling had one.

**The server-side calendar check is real:**
```json
{"fund_id":"99999999","start_date":"2026-13-45"}
```
→ `start_date must be a valid YYYY-MM-DD date (got '2026-13-45')`

This is the important case: `2026-13-45` **matches** the regex, so only a semantic calendar check can reject it. Regex alone would have let it through, exactly as noted when the root cause was filed.

**Validation fires before fund resolution.** The call above passed a deliberately invalid `fund_id` and **no fund-not-found error was returned** — the date layer short-circuited first.

**That closes this ticket's one open question.** The unmeasured case was *"malformed date against a **valid** fund — does it succeed over an undefined window or crash?"* It is now moot: the date is rejected before resolution runs, so the fund is irrelevant to the date layer.

**NEW-10 (date `pattern` inconsistency) also looks substantially addressed** — `end_date` and the four `custom_*` dates carry optional-blank patterns, and `get_fund_returns` / `get_benchmark_history` carry strict ones.

**Recommend: close as Fixed.**

## Draft comment — KS-1090 · VERIFIED FIXED, recovery path confirmed end-to-end

**QA verification on build 0.9.7 — PASS**

Re-tested independently on Claude Code (native HTTP), 2026-08-19 03:06–03:08 UTC.

**Name passed where a `bbg_id` is expected:**
```json
{"benchmark_ids":["MSCI World"],"start_date":"2024-01-01","end_date":"2024-12-31"}
```
→ `row_count: 0` · `unresolved_benchmark_ids: ["MSCI World"]` · `hint: "Pass Bloomberg ids (bbg_id / index_id). Resolve names with search_crbm_index first."`

**The hint is not just text — I followed it and it works:**

1. `search_crbm_index(names:["MSCI World"], limit:3)` → `index_id: "M1WO000G Index.USD"`
2. `get_benchmark_history(["M1WO000G Index.USD"], 2024-01-01 → 2024-03-31)` → **3 rows of real returns**, `unresolved_benchmark_ids: []`

The full name → id → data path completes. This is the recovery-candidate pattern KS-1079 wanted spread across the catalog, and it is the best-executed of the five fixes.

**The tool description was also rewritten** to warn explicitly against free-form names and point at `search_crbm_index` — fixing the discoverability half of the problem, not just the response.

**One cosmetic snag worth a follow-up.** The hint says *"bbg_id / index_id"* and `search_crbm_index`'s own description says *"the returned **bbg_id** is the value to pass"* — but the response contains **no `bbg_id` field**, only `index_id`. Harmless to a human; an agent told to look for `bbg_id` will not find it. Suggest aligning the wording to `index_id`.

**Recommend: close as Fixed**, with the `bbg_id` / `index_id` naming raised separately as documentation tidy-up.

## Draft comment — KS-1089 · HOLD — partially fixed, needs an owner ruling

**QA verification on build 0.9.7 — PARTIAL. Do not close yet.**

Re-tested independently on Claude Code (native HTTP), 2026-08-19 03:06 UTC.

| Mode | Result |
|---|---|
| `run_mode: "direct"` | `data: []` · `total_funds: 0` · `data_available: false` |
| `run_mode: "indirect"` | `data: []` · `total_funds: 0` · `data_available: false` |

**What is genuinely fixed:** the fabricated `real_return: 0.0` rows are gone. That was the actual severity driver — a response that *looks* valid and leads an agent to report 0% return as fact is worse than an error. The tool is now honest about having no data, and the root causes named in the fix report (the `use_returns` / `returns` column selection) are real bug fixes.

**What is not established:** the tool still returns **no usable data in either mode**.

**The specific thing that concerns me.** Before the fix, ~695 funds were returned (all zeros). Now **zero funds** are returned. Data was flowing and now is not. The fix included a fallback to *"the latest ranked snapshot"* when today's snapshot is empty — **that fallback is producing nothing.** Two readings are possible and the evidence does not separate them:

1. The data path is healthy and there is simply no live data right now — `data_available: false` is then correct, and this closes.
2. The data path is still broken and is now failing *honestly* rather than loudly — the tool remains non-functional, and this stays open.

**`indirect` mode is the discriminator.** It is documented as *historical*, so an empty response there is much harder to explain than an empty `direct` response at 03:06 UTC. **Please confirm whether `indirect` is expected to return historical values.** If yes, this is not fixed.

Literally the ticket's Expected is satisfied — *"real values **or** a clear 'unavailable' error"* — but a tool that always answers "unavailable" is still a tool nobody can use.

**Recommend: keep open** pending that ruling. If `indirect` should return history, re-scope to the remaining data-path defect rather than closing and re-filing.

## Draft comment — KS-1098 · Tool surface has drifted: 34 → 35

**New finding from the 0.9.7 re-test — inventory recapture is now required.**

The live catalog on build `0.9.7` exposes **35 tools**. The drift baseline (`baseline/aloha-tool-inventory-2026-08-06.md`, build `0.9.5`) records **34**.

**New tool: `get_cambridge_benchmarks`**

> Pull Cambridge Associates private-market benchmarks from `ks_model.cambridge_benchmark` (`DatalakeApi.get_cambridge_bench` / `get_last_cambridge_bench` / `get_priv_ca_bench`). Requires `asset_class` and `geography`. Optional `as_of_date`: exact match, then nearest prior date when `use_nearest` is true. Without `as_of_date`, returns matching rows capped by `limit`. Distinct from `search_crbm_index` / `get_benchmark_history` (Bloomberg CRBM indices).

| Parameter | Notes |
|---|---|
| `asset_class` | **required**, exact match |
| `geography` | **required**, exact match |
| `as_of_date` | optional, `^\d{4}-\d{2}-\d{2}$` |
| `use_nearest` | default `true` |
| `limit` | 1–1000, **default 1000** |

**Why this matters beyond the count:**

- **The drift baseline is stale.** Every future delta check compares against a 34-tool file that no longer matches production. Recapture at 0.9.7 before the re-test starts.
- **This tool has had no QA coverage at all.** It was never inventoried, classified read/compute/write, smoke-tested, or size-measured. It is a private-market benchmark surface that no story in KS-1066 touched.
- **It defaults to `limit: 1000`.** Given KS-1093 (no byte cap anywhere) and KS-1092 (unreliable `truncated`), a 1000-row default on an untested tool is exactly the shape of the existing payload problems. Measure it before anyone relies on it.

**Recommend:** add inventory recapture at 0.9.7 as an entry criterion, and add `get_cambridge_benchmarks` to the smoke-test scope.
